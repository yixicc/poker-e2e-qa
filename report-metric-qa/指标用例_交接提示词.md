## 2. 核心写法原则（必须遵守）

### 2.1 先定公式类型，再拆用例

计数 / 比率 / 分组 / 标签 / 列表等公式类型不同，正反例拆法不同。或条件按路径各写一条，不要混在一条里。

### 2.2 标题写可录牌场面，不写黑话

**禁止：** 交盲、进分子、自愿入池、套六人桌、「按口径计入」「不得计入」等套话。

**要写：** 谁在什么位置、做了什么动作、有没有翻牌 / 盈亏。

### 2.3 前置写对比数据，步骤只验目标，预期 = 具体值

| 列 | 要求 |
|---|---|
| 前置条件 | 素材里相关手数 / 分子分母 = `a`、`b`、`n`… |
| 测试步骤 | 上传 → 生成报告 → 打开「字段名」核对 |
| 预期结果 | `字段名=具体值`（如 `参与手数=n+1`、`主动参与率 VPIP=a/b`） |

### 2.4 Hero 用语

- **Hero** = 已入座、有本人手牌 / 动作的当前用户
- 旁观写：**登录用户旁观未入座**（禁止「Hero未入座旁观」）

### 2.5 位置类

写清：**场面人数 + 物理席 + 映射名**。

示例：`9人8人入座、按钮左第三席、UTG+2`

### 2.6 一种情况一条

正例 / 反例分条；平台差异分条；不要把多种边界塞进一条预期。

### 2.7 同一指标放一起；用「数据层级」区分来源

- **同一指标**（同一 `metric_code` / 中文名称）的用例全部放在同一张「测试用例」sheet，按指标聚在一起。
- 从《复盘需求测试用例》迁入时：先映射到字典指标 → 查重（场面相同不新增）→ 遗漏则补进该指标块。
- **不另开产品 sheet**；产品和报告用例用 **「数据层级」列** 区分，筛选即可。

**数据层级取值（固定枚举）：**

| 数据层级 | 用途 | 示例 |
|---|---|---|
| Session基础 | 报告 JSON：场次汇总 | 总手数、参与手数、视频时长 |
| 盈亏EV | 报告 JSON：盈亏与 EV | 单手盈亏、本场总盈亏、盈利手数 |
| GTO决策 | 报告 JSON：决策点 | 总决策次数、符合 GTO |
| 打法画像 | 报告 JSON：风格比率 | VPIP、PFR、c-bet |
| 位置数据 | 报告 JSON：按座位 | 各位置手数、各位置盈亏 |
| 对手数据 | 报告 JSON：对手统计 | 交手手数、对对手盈亏 |
| 单手牌 | 报告 JSON：单手事实 | 公牌、行动链、是否大底池 |
| 心态波动 | 报告 JSON：时段/连赢连亏 | 分段入池率、连亏后边缘入池 |
| 整包 | JSON 结构门控 | session_summary 存在 |
| 模块可用性 | 模块状态门控 | 某模块 available/degraded |
| **场次列表** | 产品：跨场聚合（字典外） | 盈利场次、累计场次、累计手数、场次净盈亏 |
| **账户计费** | 产品：余额与扣费（字典外） | Credits、会员、录屏计费、购买费用 |
| **产品交互** | 产品：UI/任务态（字典外） | 未读数、单手进度、手牌目录数 |

规则：

1. 能映射到 123 字典的 → 用字典原层级（如 `hand_profit_chips` → 盈亏EV），**不**改成「场次列表」。
2. 字典没有、但是产品验收要测的 → 层级用 **场次列表 / 账户计费 / 产品交互**；指标编码可用 `PROD-xxx` 或中文稳定编码，统计页按编码汇总。
3. 需求与现有用例场面重复 → 不新增；口径冲突 → 备注「待确认」，不写打架预期。

## 3. 术语与双平台（ClubGG / WePoker）

| 概念 | 写法 |
|---|---|
| 系统强制交盲 | 不算用户决策（总决策次数反例） |
| 用户主动过牌 / 弃牌 | 按画面结果计参与 / VPIP / 翻前弃牌等 |
| **托管** | 必须写「处于托管」+ 录屏可见托管标识；**代打不计 GTO 决策次数** |
| **ClubGG** | 无人下注 → 代 **check**；有人下注 → 代 **fold** |
| **WePoker** | 托管轮到行动常代 **fold**（含大盲面对小盲平跟也可能代弃） |
| 两款相同 | 标题 / 前置标 **两款通用** |
| 两款不同 | 标题带 **ClubGG** / **WePoker**，分别写场面与预期 |

**参与手数：** 按画面结果（盈亏、是否看翻牌等），与手动同局面同口径。  
**托管与手动的主要差别：** 是否计入总决策次数（托管代打不计）。

## 4. 改代码时改哪些文件

| 文件 | 职责 |
|---|---|
| `business_scenes.py` | 报告指标业务补全（字典内，场面主战场） |
| `product_scenes.py` | 产品层场景（场次列表 / 账户计费 / 产品交互；可后补） |
| `case_labels.py` | 模板标题 / 反例前置白话 |
| `metric_fixtures.py` | 正反例口径、机会、冲突说明 |
| `recording_phrases.py` | 录牌说法（可不进 Excel） |
| `generate_method_cases.py` | Excel 结构、表头、统计页、执行列 |

**不要**再加 `00_使用说明` / `01_不适用` / `02_录牌说法` / 单独「产品验收」sheet。  
产品用例与报告用例同在「测试用例」sheet，靠 **数据层级** 筛选。  
不适用场景只打日志，不进 Excel。

口径冲突时：**只认需求清单 / 已确认基准**；Skill 口径不当真源。未确认口径标待确认，不硬写预期。

## 5. Excel「测试用例」表结构

表头顺序固定：

1. 用例ID  
2. 指标编码  
3. 中文名称  
4. 优先级  
5. 测试方法  
6. 数据层级  
7. 是否用户可见  
8. 含义（字典原文）  
9. 统计方法 / 口径（字典原文）  
10. 测试用例标题  
11. 正/反例  
12. 前置条件  
13. 测试步骤  
14. 预期结果  
15. 对应字段  
16. **执行状态**（默认 `未执行`；下拉：未执行 / 通过 / 失败 / 阻塞 / 跳过）  
17. **时间**（默认空，测员填）  
18. **备注**（默认空，测员填）

重新生成会覆盖用例正文。若需保留历史执行记录，需另做合并策略（当前生成器默认不合并）。

## 6. 「指标用例统计」页要求

- 按指标汇总：正例 / 反例 / 合计 + 总计行  
- 非指标门控拆成：**JSON整包门控**、**模块状态门控**  
- 可按 **数据层级** 再汇总（报告层 vs 场次列表 / 账户计费 / 产品交互）  
- 应能看到**执行结果汇总与进度**（按「测试用例」表执行状态：未执行 / 通过 / 失败 / 阻塞 / 跳过、完成率等）

## 7. 从《复盘需求测试用例》迁入检查清单

- [ ] 映射到字典 `metric_code` 了吗？能映射 → 报告原层级；不能 → 场次列表 / 账户计费 / 产品交互  
- [ ] 与现有标题/场面是否重复？重复 → 跳过或合并备注  
- [ ] 是否口径冲突（如摊牌率分母）？冲突 → 先产品确认再写  
- [ ] 同一指标的新场面是否挂在同一编码下？  
- [ ] 产品层用例是否写了可验收的前置/步骤/预期（不必假装有 JSON path）  

补单条用例时仍检查：

- [ ] 标题是场面，不是口径口号  
- [ ] 前置有可手算对比数（`n` / `a/b`）  
- [ ] 步骤只打开目标字段  
- [ ] 预期是字段=值，不是长篇解释  
- [ ] Hero vs 旁观用语正确；位置写全  
- [ ] ClubGG / WePoker / 两款通用是否标清；托管不计总决策次数  
- [ ] 数据层级取值在枚举内  
- [ ] 跑生成器 + 复制到 Downloads

## 8. 明确不要做的事

- 不把 Skill 口径当真源；冲突只认需求 / 已确认基准  
- 不编造未确认口径  
- 不把「录牌说法」重新塞回 Excel sheet

- 不把 Credits/会员 等硬塞进 `hands_played` 等报告编码  
- 不主动 git commit（除非用户明确要求）  
- 与用户沟通用**中文**
